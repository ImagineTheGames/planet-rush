===============================================================================
C. THE ORIGIN, NAMED — src/ui/title-gate.ts, the door's `style` attribute
===============================================================================

    transform:translate(-50%,-50%) scale(var(--pr-gate-door-scale));
    transition:transform 1500ms cubic-bezier(.42,0,.5,1);

**A `var()` with no fallback is not a default of zero. It invalidates the whole
declaration.** A reference to a custom property that is not set, with nothing
after the comma, makes the declaration INVALID AT COMPUTED-VALUE TIME, and the
property takes its initial value — for `transform`, `none`.

The door is `position:absolute; left:50%; top:50%`, so it is placed by its
TOP-LEFT CORNER at the centre of the screen and pulled back into place by
`translate(-50%,-50%)`. With no transform at all it simply hangs off the centre
into the far quadrant. And the same declaration carries a 1500 ms
`transition:transform` — so the instant the variable arrives, the door does not
appear in the middle. It travels there.

`--pr-gate-door-scale` is written by `TitleGate.apply()`. `GateDom.mount()`
appends the overlay and writes the root's `cssText` BEFORE that. So there is a
window, inside the boot's own synchronous task, in which the door is in the
document and its transform is `none`. Whether the browser ever computes style in
that window decides whether the player sees this.

THE BEFORE-CHANGE STYLE, MEASURED — analysis/portrait-iphone-writes.json

`portrait.spec.ts` wraps `CSSStyleDeclaration.prototype.setProperty` and the
`cssText` setter and reads the door's computed transform IMMEDIATELY BEFORE each
write lands. That reading is, by definition, the value a transition would start
from:

    261 ms  cssText              (the root's layout)   BEFORE door transform = none
    261 ms  --pr-gate-door-scale = 1                   BEFORE door transform = none
    263 ms  --pr-gate-door-op    = 1                   BEFORE door transform = matrix(1,0,0,1,0,0)

  `none` before, identity after: the door's first computed transform is the
  transformless one, and everything downstream is the 1500 ms consequence.

WHY THE DESKTOP ESCAPES IT

Reading `window.innerWidth` is what forces the style resolution, and
`applyLayout` reads it — inside `gateRootLayoutCss(transform())`, evaluated
BEFORE the `cssText` it is an argument to is assigned, with the door already in
the document and its variable still unset. On a plain desktop window that read
is cheap and answers from the frame's own size. Under mobile emulation
`innerWidth` is the visual viewport divided by the page-scale factor, which is a
layout-dependent quantity — so the read flushes style and layout, the door's
`transform:none` becomes the before-change style, and the transition has
something to start from. Same code, same order, two platforms.

That last paragraph is a mechanism, not a fix, and it is the reason the fix is
not "move the read". Note that the same probe reproduces the fly-in ON THE
DESKTOP — `analysis/desktop-writes.json` shows `none` → identity there too —
because the probe's own `getComputedStyle` forces exactly the recalc the phone
gets for free. The defect is in the markup on every platform. The phone is
merely where the browser walks into it unaided.

a0-70 predicted this mechanism precisely, in its §5, and left it alone because
its guardrail said not to touch the gate. It was right about the mechanism and
right to flag it. This brief is what makes it actionable: it is filmed now.


===============================================================================
D. THE FIX — commit 13dcf5d
===============================================================================

Every `var(--pr-gate-*)` in the markup now carries a fallback, and the fallbacks
are not typed out: they come from `gateVars('locked', 1)` — the sealed door's own
ten values, the state this screen is first painted in — through one helper, so a
fallback cannot drift from the phase it is the fallback for.

    transform:translate(-50%,-50%) scale(var(--pr-gate-door-scale, 1));

The point is not merely that the declaration is now valid. It is that the first
computed value is byte-for-byte what `apply()` writes a moment later, so there
are not two computed values, and a transition with nothing to interpolate
between never starts. That is why the fix is a fallback rather than a
`transition:none` on first paint: the second would hide the jump, this removes
it.

  Scope. Nine properties: door-scale, door-op, leaf-top, leaf-bot, hub-rot,
  hub-scale, bolt-scale, haz-op, prompt-op. (`--pr-gate-cursor` already had one;
  `--pr-gate-vw`, `--pr-gate-vh` and `--pr-gate-safe-bottom` already had theirs,
  documented in `vw()` for this exact reason — the file already knew the rule,
  in one half of itself.)

  What it cannot change. From the first press onward every one of these
  properties is set on the root, and a fallback that is never reached cannot
  change what a set value does. a0-50's opening is untouched, which §E measures
  rather than asserts.

WHY A SECOND INSTRUMENT. CDP screencast only emits a frame once the previous one
is acked, so the single frame this report is about is exactly the frame it is
entitled to drop — the gaps in `frames/before/gated/` are real. `firstframes`
replaces it with a readback that cannot drop a frame: `getContext` is wrapped to
force `preserveDrawingBuffer` (without it `toDataURL` on Pixi's canvas reads
back empty and every frame looks blank, which is its own way of lying), and the
sample is queued from `setTimeout(0)` INSIDE a `requestAnimationFrame` callback.
Every rAF callback in one frame runs in a single task, so that timeout lands
after Pixi's renderer has drawn. Frame n in those directories is animation frame
n of the real boot. Nothing in `src/` is patched to make it work.

===============================================================================
3. WHAT THE GATE DOES — frames/before/motion.json, exact-open/ticks.json
===============================================================================

The gate is a DOM overlay above the canvas, so anything it did would be a DOM
transition, and the browser will report those directly rather than by inference
from pixels. `motion.spec.ts` listens for `transitionrun`, `transitionstart`,
`transitionend`, `transitioncancel` and `animationstart` in the capture phase on
`document`, installed before a line of app code runs.

  first 3 s:   transition* events ......... 0
               animationstart ............. 3
                 pr-gate-sheen  x2   (the wordmark's sheen pass — by design)
                 pr-gate-prompt x1   (PRESS ANYWHERE TO ENTER — by design)

  Zero transitions. Nothing on the page eases anywhere.

The one instant no frame loop can reach is inside the boot's own synchronous
task, when the overlay is inserted. A `MutationObserver` on `#app` catches it:

  253 ms  inserted  div#pr-title-gate
          --pr-gate-door-scale = "1"
          #pr-title-gate-door  computed transform  matrix(1,0,0,1,-610.633,-376.93)
          rect [242.9, 72.1, 1221.3, 753.9]  →  centre (853.5, 449.0)
          viewport centre (853.5, 449.0).  Offset: zero.

This is worth stating precisely, because it is the near-miss. The door is
written `left:50%; top:50%; transform:translate(-50%,-50%) scale(var(--pr-gate-door-scale))`
with `transition:transform 1500ms` and that custom property has NO fallback. If
the variable were ever unset while the element was in the document, `transform`
would be invalid at computed-value time, resolve to `none`, and drop the
element's top-left corner onto the screen's centre — the bottom-right quadrant —
and the 1500 ms transition would then carry it back. That is a perfect match for
the report's words and its one-second window, and it is what I expected to find.

It does not happen. `GateDom.mount` inserts the element and `TitleGate.mount`
calls `apply()` in the SAME synchronous task, with no forced style recalc
between them, so the browser computes the element's style exactly once and it is
already correct. The measurement above is that fact, and the zero transition
events are the same fact from the other side.

And through the opening, the door grows in place (exact-open/ticks.json):

  f7    620ms  rect  242.9   72.1  1221.3   753.9   centre 853.5,449.0
  f39  3136ms  rect  225.3   61.2  1256.3   775.5   centre 853.5,448.9
  f47  3599ms  rect  -76.5 -125.0  1859.9  1148.1   centre 853.5,449.0
  f55  4047ms  rect -491.1 -381.0  2689.2  1660.0   centre 853.5,449.0
  f63  4496ms  rect -618.0 -459.3  2943.1  1816.7   centre 853.5,449.1

  The rect grows by a factor of 2.4 and its centre moves 0.1 px. Candidate 3's
  failure mode — "a scale applied about the wrong origin moves content toward a
  corner rather than growing it in place" — is absent, and this is the number
  that says so. a0-50's opening is untouched, as the guardrail requires.

4. THE THREE CANDIDATES, EACH CLOSED BY A MEASUREMENT
===============================================================================

1  FIRST-FRAME LAYOUT.  CLOSED.
   The first frame that draws any ink is already at the final layout, at four
   different boot speeds (production 1x, production 1.5x, dev server, and a boot
   whose viewport changes underneath it at 120 ms). There is no "defaults on
   frame 1, snap on frame 2": frames are byte-identical from the first inked one
   — 328150 ink px at 1x and 732424 at 1.5x, unchanged for the length of every
   film. `readViewport()` is not on this path at all; it belongs to the match
   boot. The menu reads `ctx.logicalSize()`, which is derived from `app.screen`
   after `Application.init({resizeTo: window})` has already sized it.

2  THE ROOT TRANSFORM.  CLOSED.
   `window.__mainMenu` reports `rotated: false` and
   `logicalViewport {width: 1707, height: 898}` on every sampled frame. The
   desktop takes the identity branch, as it must. The rotated branch's `x: physW`
   would put content one whole screen width to the right, which is the exact
   fingerprint the brief describes — it is not being hit, and assertion 1 of the
   new test now fails if it ever is.

3  THE TITLE GATE'S PHASES.  CLOSED, and it was the likeliest.
   Zero transitions in the first three seconds. The door is centred at the first
   observable style computation, 253 ms in, inside the boot's own task. Its
   centre moves 0.1 px while it scales by 2.4x. And with `?gate=0` — no door on
   the screen at all — the menu still appears already centred, so the gate is not
   what places it either way.


===============================================================================
5. THE DELIVERABLE THAT IS MISSING, AND WHY
===============================================================================

The Definition of Done asks for a test that FAILS on today's code. There is no
such test to write, because the defect it would have to catch is not in today's
code on any axis I could film. Writing one that passes and calling it a
reproduction would be the four-round star-bloom failure again, one lane over.

So the test on this branch is a REGRESSION GUARD and is labelled as one in its
own comment. It is real work and it holds a real property that nothing held
before — but it is not proof of the reported bug, and this audit will not let it
be read as such.

DIRECTOR: this needs the developer's own conditions before another round is
spent on it. Specifically:
  - browser and version (everything above is Chromium 131 via Playwright);
  - was it a clean load, or a reload / a restored session / a second monitor;
  - `?gate=0` or the real front door;
  - whether the window was being moved or resized in that first second;
  - and ideally the developer's own capture, since it is a one-second window on
    the first screen and it is cheap to film.

There is one thing above that is a real latent fragility even though it is not
firing: `--pr-gate-door-scale` has no fallback in a declaration that carries a
1500 ms `transition:transform`, so the gate's correctness rests on `apply()`
staying in the same synchronous task as the insertion. Any future edit that puts
a style read (or an `await`) between them turns that into precisely the reported
symptom. It is `title-gate.ts` — a0-50's file, not mine — and the guardrail says
not to touch the gate's opening, so it is flagged here rather than changed.
